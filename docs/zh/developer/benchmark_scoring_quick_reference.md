# Aventine 评分标准中文速查

这份文档回答一个问题：**每个数字究竟在评价模型、翻译 recipe，还是评测系统本身的什么能力？**

> 当前原则：Aventine 排的是完整 recipe，不是脱离 prompt、推理强度、上下文、repair 和
> validator 的裸模型。页面尚未拥有正式综合分；任何 PREVIEW 分数都不能冒充已落地结果。

## 一分钟速记

| 指标 | 主要评价能力 | 看到失败时先想到什么 |
| --- | --- | --- |
| 执行成功率 | API/本地运行稳定性 | 超时、429、服务异常、空响应；不等于语言能力差 |
| 结构化输出成功率 | 指令遵循与输出协议控制 | JSON/数组格式、条目数、schema 不合格 |
| 硬校验通过率 | 游戏本地化工程安全 | 变量、颜色标签、占位符、换行、条目结构被破坏 |
| 质量约束通过率 | 明确任务要求的满足能力 | 术语、上下文消歧或其他可确定内容约束未满足 |
| 匿名胜/负/平 | 相对软语言质量 | 语义、自然度、语气、文体和上下文整体较量 |
| Repair 硬通过率 | 在约束下修好指定错误 | 能否准确修复且恢复合法结构 |
| 有效条目保持率 | 克制修复、避免过度编辑 | 修坏原本正确的条目或擅自重写 |
| 参考修复精确命中率 | 修复精确度 | 是否恰好恢复到冻结参考答案；不是一般翻译质量 |
| 多次运行稳定性 | 输出方差与可重复性 | 单次抽风还是稳定弱点 |
| 术语发现率/误报率 | Remis 新词挖掘工作流 | 是否找全候选新词、是否制造大量垃圾候选 |
| 耗时、Tokens、成本、速度 | 部署效率 | 达到同等质量需要多少资源 |
| 有效裁决覆盖率、位置一致性 | **裁判质量** | 评价 judge 是否可靠，不是参赛模型得分 |

## 当前 Remis 冻结小样本实际测了什么

### 1. 执行状态

- `completed`：模型调用完成，且结果可进入后续评分。
- `execution_failure`：调用抛出异常、超时或供应商失败。
- `structured_output_failure`：模型有返回，但无法解析为要求的字符串数组，或条目数不一致。

它把**服务可用性**和**指令/协议遵循**从语言质量中拆开。不能把 429 记成翻译错误，也不能把
“写得很好但没按格式返回”当作可部署成功。

### 2. 硬校验通过率（Hard Reliability）

主要检查：

- 受保护 token、作用域变量和 placeholder 是否数量一致；
- `§Y...§!`、`#r ...#!` 等颜色标签是否完整、成对且字符精确；
- 转义换行、条目数和结构是否保持；
- Remis validator 是否产生阻断级 error。

这是**工程安全和约束遵循**，不是文采分。硬校验失败的候选不能靠 LLM judge 的审美翻盘。

### 3. 质量约束与 contextual glossary

当前 glossary 陷阱题同时检查五个条件：

1. `France → 法兰西`：服从项目指定译名；
2. `Texas → 得克萨斯`：服从项目指定译名；
3. `prestige goods → 名贵商品`：识别完整游戏经济术语；
4. 农场里的 `silo → 筒仓`：**上下文应覆盖词典注入的军事义“发射井”**；
5. `missile silo → 发射井`：军事语境中继续服从词典。

因此“该题 0/5”不等于所有术语都错。当前规则是合取：任一子条件失败，整题
`quality_constraint_pass=false`。例如 Nemotron 五轮均在第四项机械服从词典，把装小麦的
`silo` 译成“发射井”；它并没有把其他术语全部译错。

这项主要评价：**词典遵循、复合术语识别、词义消歧，以及在明显上下文证据面前克制地覆盖错误词典**。

### 4. 匿名成对胜/负/平（Soft Preference）

只有双方都执行成功且硬校验通过时，才把匿名 Candidate A/B 交给裁判。裁判主要比较：

- 语义准确与信息完整；
- 术语是否正确且一致；
- 流畅度、自然度和目标语言地道程度；
- 人物声音、文体、语气、register 和游戏氛围；
- 上下文与篇章一致性；
- repair 中是否出现不必要改写。

同一题会交换 A/B 顺序再判一次。两次归一化结论一致才记胜、负或平；不一致记
`unresolved`。裁判输入没有参赛模型名称。

### 5. Repair track

Repair 主要评价**在明确约束下的指令遵循**，但不只等于一般 instruct 能力。它同时要求：

- 找到被注入的具体结构错误；
- 恢复缺失或损坏的 token/标签；
- 保持正确条目不变；
- 不借修复之名重译整段；
- 输出仍满足结构化协议。

相关信号：

- `hard_pass`：修完后结构是否真的合法；
- `valid_items_unchanged`：原本正确的条目是否保持不变；
- `reference_exact_match`：是否精确恢复冻结参考修复；
- `over_editing_rate`：是否修改了本来无需修改的内容。

所以 repair 10/10 可以支持“模型的约束型 instruct/编辑能力不错”，但不能外推为整个通用
instruction-following benchmark 的 10/10。

### 6. 多次运行稳定性

同一 recipe、同一参数、同一冻结题重复 3–5 次，用来区分：

- 稳定能力或稳定弱点；
- 单次随机波动；
- 供应商限流与模型失败；
- 语言结果、格式结果和耗时的方差。

模型、prompt、推理强度或采样参数改变后，应视为新 recipe，不能混入同一稳定性统计。

## 页面上的哪些指标不是参赛模型语言分

### 裁判健康指标

- **有效裁决覆盖率**：需要裁判的题中，有多少得到位置一致、可采用的结论。
- **位置一致性**：交换 Candidate A/B 后，裁判是否仍支持同一真实候选。
- **schema/截断失败率**：裁判能否稳定输出合规结果。
- **校准准确率、严重错误召回、false-good**：裁判对 MQM/ACES 人类或对比金标的贴合程度。

这些数字评价的是**尺子是否可靠**，不能加到参赛模型的质量分里。

### 运行与部署指标

- 总耗时、平均延迟、生成速度；
- 输入/输出/推理 Tokens；
- 估算成本、显存和量化；
- 供应商失败率与限流情况。

它们评价**达到某个质量水平的代价**。现阶段适合做 Pareto frontier、筛选器或 badge，不能
偷偷替代语言质量。

### Recipe 元数据

模型、具体 revision、量化、prompt、测试集、语言方向、上下文策略、裁判与裁决规则都是
复现条件，不是分数。任何一项变化都可能形成新的 recipe 条目。

## Remis 新词挖掘机指标

“术语发现率”不是 Aventine 翻译器原生能力，但可以作为紧密绑定的 Remis workflow signal：

- **术语发现率/Recall**：人工确认的新词中，被系统发现了多少；
- **术语精确率/Precision**：系统提出的候选中，有多少是真术语；
- **术语误报率**：候选中有多少是普通词、重复项或无意义片段；
- **规范化/去重正确率**：屈折变化、大小写和别名能否归并；
- **上下文释义质量**：是否给出正确领域义，而非只抽出字符串。

它应独立展示，不能和 glossary adherence 混为一谈：前者测**发现候选术语**，后者测
**翻译时正确使用已知术语**。

## 2026-08-01 四模型稳定性试跑应如何解读

四位参赛模型使用相同 profile：OpenRouter `chat.completions`、`max_tokens=4000`、
`reasoning.enabled=false`、`reasoning.exclude=true`、客户端重试为 0。因此：

- Luna 的 repair 1/10 是**无推理 recipe** 的结果，不能直接代表开启 reasoning 后仍然如此；
  具体失败主要是把 ASCII `§!` 写成全角 `§！`，或移动/遗漏颜色标签。开启 reasoning 后应作为
  新 recipe 单独复测。
- DeepSeek Flash 的 repair 10/10 说明当前后训练在结构修复、约束遵循和克制编辑上表现很好；
  它支持“约束型 instruct 能力不错”，但不是通用 instruct 总分。
- Nemotron 的 contextual glossary 0/5 主要来自农场 `silo` 消歧陷阱 0/5，不是术语全部失败。
- Ling 同时出现结构化输出失败和较低硬校验率；在当前小样本与 profile 下缺乏竞争力。

## 计划中的扩展能力

| 计划维度 | 评价能力 | 归属 |
| --- | --- | --- |
| European：FR/DE/RU/ES/PT/TR | 欧洲语言方向的翻译泛化 | 模型/recipe |
| East Asian：ZH-CN/JA/KO | 东亚语言方向的翻译泛化 | 模型/recipe |
| Batch Cohesion | 单 batch 内称谓、代词、术语和 voice 一致性 | 模型/recipe |
| Cross-batch Drift | 无状态分批后的一致性退化 | Remis 工作流/上下文策略 |
| 长文本与约束压力 | 难度上升后的质量保持和结构安全 | 模型/recipe |
| 语义陷阱 | 否定、数字、实体、遗漏、添加、fluent-but-wrong | 模型/recipe |
| 修复克制 | 是否只改错误部分 | 模型/recipe |
| 难度/能力曲线 | 小模型到旗舰模型的区分度与饱和点 | benchmark 设计 |

英语通常作为源语言或控制语言；“模型擅长英语”不等于无需测试英译质量，尤其当目标是人物
声音、历史 register 或游戏专有语境时。但区域榜单的主要区分度可以集中在非英语目标语言。

## 综合分：现在还没有正式版本

历史 Pilot 展示公式曾使用：

`100 × (0.60 × Soft Preference + 0.40 × Hard Reliability)`

它只能作为设计起点，不能直接替换网页 PREVIEW 数字。正式 aggregate 至少必须记录：

- `score_version`、测试包/hash、recipe/hash；
- 分项分数、样本数、有效裁决覆盖率与置信区间；
- 运行/结构化失败数和失败规则；
- 区域分、稳定性和上下文预算元数据。

当前讨论中的失败规则也仍是待版本化政策：

- 翻译阶段可恢复的硬校验/结构化失败：该题语言分乘 `0.67`；
- 空响应、条目错位、不可恢复或执行失败：该题 `0` 分；
- 校对/repair 阶段硬校验或结构化失败：该题 `0` 分。

在 aggregate 实际产出并通过校准前，页面应继续标记 `PREVIEW`，成本、速度、术语发现和
Cross-batch Drift 也应保持独立维度。
